# M1.3 — Dock blocker decision

## Evidence

The M1.2 `workbench` plugin creates a normal vertical split. The split tree,
pane list, layout, rendering, and mouse dispatch all belong to one `Tab`.

The following scenarios were reproduced:

1. Open `workbench` in tab A, then create and switch to tab B. The sidebar
   remains in tab A and tab B has no sidebar.
2. Open `workbench`, create another editor split, then run `workbench` from
   that split. Two independent sidebars are created.
3. Sidebar width is ordinary proportional split width and can be changed by
   the normal split-resize gesture.

## Decision

The first two scenarios are architectural blockers: they violate the product
requirement for one persistent left sidebar shared across editor tabs. The
third is prototype polish, not a blocker by itself.

Do not add plugin-side synchronization or replicate a sidebar into every tab.
That would still create separate panes and state, and cannot own one
application-level layout or lifecycle.

Add one optional, generic application dock primitive in a new M1.4 task. It
must not contain Workbench, Explorer, Search, Git, or LSP behavior. When no
dock is attached, Micro's existing tab and split behavior must be unchanged.

## Compatibility

The proposed primitive is additive and dormant by default. It changes no
existing settings, keybindings, themes, plugin behavior, or normal split
layout until a plugin attaches dock content.
